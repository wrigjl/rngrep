## Headline `compile_time` crates (the rr-defeating category)

All 10 x86 `compile_time` crates were checked against real source; each
is a genuine `#[target_feature(enable=...)]` (CPUID-elided) gate
(`target_feature_attr=true` at the site), **not** a `docsrs`/`doc(cfg)`
misfire -- the `cfg_attr` bug that produced the May `safe_arch` false
positive was fixed before this run and does not recur.

- Carried over from May, unchanged: `getrandom` 0.4.3, `rmath`,
  `typed_arch`, `concrete-csprng`, `tfhe-csprng`, `vektor`,
  `hyper-thread-random`.
- New on this snapshot, audited genuine: `foundation_compact` 0.2.0
  (a near-verbatim copy of `getrandom`'s `rdrand` backend -- same
  `#[target_feature]` retry loop), `lib-q-random` 0.0.8
  (`#[target_feature(enable="rdrand")]` fns), `hardware-rust-crypto`
  1.0.1 (`#[target_feature(enable="rdseed")]` fn).

`getrandom`'s `compile_time` verdict is additionally confirmed in machine
code (SGX object: 120 RDRAND, 0 CPUID).

## Emit/no-emit soundness

**Zero contradictions** on the observable subset, both ISAs
(`verify_summary`-style rollup over `verify_results.csv` +
`verify_refine.csv`): no crate the classifier called an emitter proved

## Interprocedural over-count caveat -- unchanged at 3 crates

The function-local rule labels a site `unconditional` when its runtime
guard sits in a different function (in `std`). Binary verification
catches these as `cpuid`-present / RDRAND-absent objects. On this
snapshot the same **three** x86 crates exhibit it -- `urng` 0.8.0
(`cpuid`x10, RDRAND 0, all-features build), `x64` 0.16.2 and `x86_64`
0.15.4 (`cpuid` 2-4, RDRAND 0, nightly build; both `fail-lib` on stable
via `#![feature]`). Always an **over**-count of `unconditional`; per-site
numbers unaffected. So the paper's "three of the 40" becomes **three of
the 46**.
